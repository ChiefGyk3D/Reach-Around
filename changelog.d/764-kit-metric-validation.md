- Validate media-kit metric definitions and add size limits (#764): a kit takes one `source: counts` metric per platform, metric labels are compared after Unicode normalization, case folding and whitespace collapsing, and the site config caps tabs (50), blocks per tab (200), links per section (200) and socials (50). Config problems print at most 20 entries plus a count of the rest, and none of the new messages repeat the offending value. `docs/site.schema.json` regenerated. The whole site config is also held to a 256 KiB file limit (refused before parsing) and, before any model is built, to a 20,000-value budget, a 64-level depth limit and a plain shape (mappings with text keys, lists and scalars only; tuples, sets and other containers are refused), so the per-list caps cannot multiply into millions of links. The error list is built only when it holds at most 1,000 problems (a longer one prints a count), so error materialization is bounded. Config error paths never print a key from the file (an unknown key shows as `<unknown field>`; other segments are escaped, cut and capped), and pydantic model instances are refused in raw config input. Printed config problems are fixed sentences chosen by the error type (never pydantic's own message, which can echo a value); a validator's reason is matched against a short list of known reasons and otherwise prints a generic sentence. The config budget also bounds scalar size (one text, key or integer over 65,536 characters, or 262,144 in all, is refused; scalar subclasses are refused). Every way a config or an imported history is built now runs the budget: it sits in a before-validator on both models, an existing model instance is refused (so a `model_construct` object cannot be passed back in), one function (`validate_site_config`) is the only loader entry, and a test fails if any code in `src` calls `model_construct`. The imported-history file gets its own budget (4,000 values, 6 levels, 256 characters per scalar). Error paths print only schema names (any other segment, including a mapping key, shows as `<key>`), and the YAML loader no longer echoes a duplicate key, tag or parser sentence unbounded. The docs now say which error-work bounds are enforced (and boundary-tested) and which are only sampled. JSON entry points (`model_validate_json`) refuse an over-size document before parsing, located validator reasons share the 20-problem print cap, and the source guard resolves aliases, renames and `getattr`. The JSON byte cap is measured in encoded UTF-8 bytes. `TypeAdapter` and `validate_json` are not a supported way in (a source guard fails on any use in `src`); the guard also catches module-qualified construction and module names joined from constant strings, scopes each owner module to its own class, and the cut-off count of omitted problems is exact (or says "and more problems" when it cannot be known).
