- The D1 backup script now checks that an export is complete (#944). A table may gain rows during the run but must not lose any: if a table's row count after the exports is below the count before, the run fails (exit 1, rerun). Each export file's rows, counted by reading it line by line without executing anything in it, must lie between the before and after counts, so an export that ends early fails the run instead of producing a short backup. The file is opened once without following a link and read under one byte budget shared by all the export files of the run (`BACKUP_MAX_BYTES`, default 1 GiB, a whole number up to 1 TiB, else exit 2) and a 1 MiB line limit. A NUL byte, invalid UTF-8, an unbalanced quote, several rows in one INSERT, or an INSERT or REPLACE word outside quotes anywhere but in the exact accepted statement (a CTE-prefixed insert, `INSERT OR ...`) fails the run. The row-count answer must name every exported table exactly once and nothing else, or the run fails before any export is trusted. The accepted one-INSERT-per-row grammar was verified against real D1 exports on 2026-11-27. A delete plus an insert that leaves the counts level during the run is a documented residual. Documented limit: with growth during the run the row count proves cardinality only, not that every older row is present; whether a running D1 export is one consistent snapshot is inferred, not documented. The table listing now also carries each table's definition and is taken again after the exports: a table that was dropped, added or replaced during the run fails it. A listing or count answer is trusted only when it is exactly one successful result, never an error object, several results or a failed result. The backup script's note on the ignored `_cf_KV` table now says what ignoring it means. The post-deploy smoke script now requires the content type to be exactly `text/html` (parameters allowed) and the nosniff header value to be exactly `nosniff`; values that only contain those words no longer pass.
