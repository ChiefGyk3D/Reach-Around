- Analytics rollup and retention bookkeeping is more robust (#759, epic #749): late rows above a day's counted id that are deleted at the retention ceiling are now flagged (`rollup_overdue`) and counted (`rollup_overdue_rows`, cleared with the flag), the count and flag are computed with a `SELECT COUNT(*)` over the same row picker as the delete (same predicate and limit, built once) and committed with it in one `db.batch()` transaction, so a failure cannot lose the count and nothing depends on cross-statement `changes()`; a day gets an explicit re-roll closed state (`view_rollup_log.reroll_closed`, new migration `0018`, plain column add) that is set when a late batch is dropped or the seal window ends (48 hours after `ROLLUP_GRACE_HOURS`), so a later batch cannot re-roll a day over correct aggregates; every bounded aggregate, hour and log delete is keyed by the table's whole primary key, so a day of many sites goes a batch at a time; click retention deletes in fixed batches (500 rows, at most 10 per run) with a `click_purge_backlog` marker in `view_meta` that every run reconciles (one extra query) so it is never missing or stale for longer than a run; the hourly pattern table is built only from rows up to the day's counted id, so it agrees with the daily tables. Write budget model unchanged: no new rows per operation (the closed state rides in the log row's existing write; the counters and the marker are written only when the ceiling or a backlog is hit), so `budgetcheck` and the pinned figures did not move. Click purge options can only lower the per-run bounds (non-finite values are refused), and the documented click purge cost is corrected to 2 queries when idle. A day's rollup log row is now deleted only once no aggregate, city or raw row of that site and day is left, so the independently bounded deletes cannot orphan data from its checkpoint.
