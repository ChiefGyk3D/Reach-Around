- Instance template: a labeled, tombstone-only rewrite of the counts history is now accepted, and every other rewrite is refused (#619, epic #364, follows #586). New engine command `counts history-compare` (exit 0 append-only, exit 10 valid rewrite, anything else a refusal; counts only in its output) checks the exact bytes: only `api` records may become tombstones (their corrections go with them), every kept line keeps its content and order, no tombstone is removed or turned back into data, later lines are re-chained and canonical, at most 500 records and 10 percent per rewrite, and every tombstone field and one committed manifest are derived from the redacted keys, a closed reason code and two dates, so a redacted value has no field to hide in; the matching `numbers.json` entry must be removed in the same change. `counts history-redact --derived` checks every manifest condition first (a real `redactions` folder opened without following a symlink, no existing manifest, writable), writes the manifest to a private temporary file, replaces the history file, then installs the manifest without overwriting, and names the one recovery step if that last step fails. New instance workflow `history-guard.yml` (one job, check name `History guard`, read-only token that also reads workflow runs, `pull_request` only) reads its scripts and `.github/history-approvers` from the base commit and accepts a rewrite only with the `history-tombstone` label applied by a listed login after the head commit last changed and at least 24 hours earlier (a new head needs the label applied again), from a `redact/` branch in the same repository, with no open bot refresh pull request, exact allowed paths, a head that contains the current `main`, the label state read twice, and `main` read again just before every acceptance. The job summary shows short commit ids and counts, no login. Which workflow revision GitHub runs for a pull request that edits it is marked unverified until the live gate G1. Documented in the instance template README and `docs/social-history.md`. The workflow alone is not a sufficient merge gate: the README and the workflow header now say so, list the trust boundary the instance owner must configure and carry a checklist to finish before the first approver is listed, and the job first compares the running workflow with the base copy. The writer also makes the manifest and a new folder durable before the rewrite and prints a no-overwrite recovery command, and the Actions run listing is paged, following only next-page links that keep the first request's https host and path. The controlling boundary is CODEOWNERS plus mandatory code-owner review of the paths that protect the guard (`.github/`, `scripts/`, `engine.lock`, `engine.release.json`, the approvers file and `history/redactions/`; the history file itself is not owned, so the daily refresh needs no review) (the author cannot satisfy it, stale approvals are dismissed, approval of the most recent reviewable push is required, administrators are included); the template ships an example `.github/CODEOWNERS`. The ruleset required workflow ("Require workflows to pass before merging") is documented as not available on a Team plan and as an optional upgrade for Enterprise accounts only. The label is described as an intent record and a 24 hour cooling-off signal, not a gate GitHub enforces. The README has a section for an owner who is the only person (GitHub does not let an author approve their own pull request; a second account the owner controls is the strongest working option, each option's limits are stated, and bot or App reviewers are marked unverified), and the activation checklist demands the CODEOWNERS file, the branch rule and an observed unmergeable test pull request before any approver login is added; live gate G1 is optional and recommended. Restricting who can push `redact/` branches stays defense in depth only. Recovery guidance now names the full folder path of the manifest instead of a bare `redactions/`. An interruption after the history file was replaced no longer removes the staged manifest: the run keeps it and prints the recovery step. A failure or an interruption while the manifest is given its final name now prints guidance for the state actually reached, read from the folder: both names present (compare with cmp, then remove the temporary name), or only the final name present (installed; sync the folder or run history-verify), and the folder descriptor is always closed. The design gates that need a live GitHub test repository (G1, G2, G4 to G6) are not yet run; see the spec.
