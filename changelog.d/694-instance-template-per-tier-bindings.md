- Instance template deploys through the reusable Worker workflow (#694, epic #246): `examples/instance-repo/.github/workflows/deploy.yml` no longer runs the Worker deploy inline or reads a `CLOUDFLARE_API_TOKEN` GitHub secret. It has two tiers, `staging` and `production`, each its own environment and its own secret-manager identity (OIDC, one identity per tier; config `dev` for staging, `prd` for production). `worker-<tier>` calls `ChiefGyk3D/Reach-Around/.github/workflows/deploy-worker.yml` pinned to the commit in `engine.lock` (with `# v0.3.0-rc.6`); `pages-<tier>` publishes the site, with the token as one masked output mapped into the publish step only. Staging runs on a push to `main` or by hand with target `staging`, only while `ALLOW_STAGING_DEPLOY` is exactly `true`. Production runs only by hand on `main` with target `production` and only while the repository variable `ALLOW_PRODUCTION_DEPLOY` is exactly `true` (absent by default, so production is off). `id-token: write` is held only by the four deploy jobs. The `validate` job hands the engine pin to the others and fails when the two Worker names are equal, are not plain names, or are the engine's test Worker, and when `STAGING_PAGES_PROJECT` equals `PRODUCTION_PAGES_PROJECT` (lowercased, whole value); the staging Pages job refuses the production project. The template's `engine.lock` moves to `0.3.0-rc.6` (image digest read from the registry), Renovate groups the two call pins with it, and the template test accepts a pre-release version comment (`-rc.N`, `-alpha`, `-beta`; a bad suffix still fails). New tests keep the call pin equal to `engine.lock`, all shared-repository pins on one commit, the caller permissions at least what the called workflow declares, no `secrets` anywhere in `deploy.yml`, production unreachable from a push, and `id-token: write` on the four deploy jobs only. Docs: the template `README.md` (environments, repository variables for both tiers, `ALLOW_PRODUCTION_DEPLOY`), `docs/instance-repos.md`, `docs/deploy.md`. Existing instance repositories: nothing changes until you copy the new workflow and set the variables; the old repository secret for the Cloudflare token and the variables `PAGES_PROJECT`, `D1_DATABASE_ID`, `RATELIMIT_NAMESPACE_ID`, `SITE_HOST` and `ZONE_NAME` are no longer read.
  - Tier schedule wording (#694): the deploy documentation and workflow comments say exactly when each tier runs. Staging runs on a push to `main`, or by hand on `main` with target `staging`, only while `ALLOW_STAGING_DEPLOY` is exactly `true`; otherwise only `validate` runs. Production runs only by hand on `main` with target `production` while `ALLOW_PRODUCTION_DEPLOY` is exactly `true`. New tests read the parsed workflow and bind every deploy input of every deploy job to exactly one validate output or literal per tier (staging jobs read only staging outputs, production jobs only production outputs), fail when a production job reads a staging output, and fail when an input is added until it is mapped.
  - Environment setup (#694): the README and `docs/instance-repos.md` say to create and protect both environments (required reviewer, **Prevent self-review**, `main`-only) before the first push and to set `ALLOW_STAGING_DEPLOY` last, because GitHub creates a missing environment unprotected on first use. The README says what environment protection can and cannot guarantee for a sole owner. Independent approval needs a second human; environment protection and **Prevent self-review** do not establish that the approver did not author the commit, and "not the author" must be enforced by protected-branch pull-request review or an external policy in addition. A sole owner's approval is a confirmation pause only.
  - Caller and callee permissions (#694): the permission test reads the callee's permissions straight from `git show <ENGINE_REF>:.github/workflows/deploy-worker.yml`, fetching the commit when the checkout lacks it; a missing commit fails the test when the `CI` variable is set and skips with a message otherwise. The committed fixture `tests/fixtures/instance_template/callee_permissions.json` is only an aid and must equal those permissions. A new test shows a newly required callee permission (`packages: read`) fails the compatibility check.
  - Tier settings are checked before any deploy (#694): `scripts/check-tiers.sh` compares staging and production settings after normalization (lowercase; one trailing dot and a default port removed from hosts and zones; non-ASCII names must be written in `xn--` form; rate-limit namespace ids are ASCII digits compared as integers). Required settings must be present: staging always, production as a set once any production setting or `ALLOW_PRODUCTION_DEPLOY` is set. The script runs in `validate` before any deploy job and requires the staging and production settings to differ. `validate` writes the checked values as job outputs and the four deploy jobs read only those outputs, so the checked values are the values deployed. New tests cover each rule, and the release-tag tests assert the exact grammar error and fail when the grammar is loosened.
  - Engine identity fixed values (#694): the engine repository is `ChiefGyk3D/Reach-Around` and the image path is `ghcr.io/chiefgyk3d/reach-around`. The deploy workflow and `scripts/read-lock.sh` use these fixed values.
  - Release candidate tags (#694): `scripts/read-lock.sh --release` accepts a release-candidate tag `vX.Y.Z-rc.N` as well as `vX.Y.Z`. The grammar is `^v[0-9]+\.[0-9]+\.[0-9]+(-rc\.[0-9]+)?$` over the whole value and nothing else passes (no other suffix, no whitespace, no newline); the `# vX.Y.Z[-rc.N]` comment on `ENGINE_REF` follows the same grammar.
