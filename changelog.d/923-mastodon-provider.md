- Fediverse collector slice 3, the Mastodon provider (#923, design in `docs/design/fediverse-collector.md`, epic #244). New `reach_around.counts.mastodon_feed` reads one public account on a Mastodon-API instance named in config, with no login: one `accounts/lookup` call (skipped when a numeric account id is configured, which then reads no follower count) and up to twelve `accounts/:id/statuses` pages of 40, built with `exclude_replies`, `exclude_reblogs` and a numeric `max_id` cursor taken from the smallest id of the previous page. The instance host must be a public lower-case ASCII DNS name (no IP literal in any notation, no local suffix, no port, userinfo, path or trailing dot, no non-ASCII spelling) and the account a plain local name; both are checked again before any request. The whole run shares one budget of 13 HTTP requests, retries and redirect hops included, and one absolute monotonic deadline of 90 seconds covering the pauses, the retry waits and every request; a response that arrives after the deadline is discarded. The walk never trusts ordering to stop early: it ends only at an empty page or when a budget ends it, so an account with more statuses than the page budget holds (12 pages of 40) reports `page_cap` incomplete by design and keeps its prior values. A `Link` header or any URL in a body is never followed. Boosts, posts by other authors, replies to other accounts and non-public posts are never counted; a malformed or unknown status makes the whole read incomplete (`bad_shape`), checked field by field through one path before any status is counted or skipped (so an old, foreign, hidden or boosted status is checked too, and a reply marker or boost marker that is present must have the right type), and an incomplete read keeps the prior rows and is never a zero. A status listed twice keeps one row with the elementwise maximum of its counts (the counts of one status only grow, so the order never matters), and copies that disagree on whether it counts end the read as `bad_shape`. A missing or malformed profile count in the lookup is `bad_shape` too, never a complete read. A missing or skewed server `Date` is `clock_skew`, a low `X-RateLimit-Remaining` is `rate_limited` (a present value that is not 1 to 10 ASCII digits is `bad_shape` and never raises), a moved or suspended account is reported and never followed. The anonymous snapshot (counts, a date, a flag and a fixed reason word; no host, account, id, text or time) passes a recursive guard and the same consistency table as the Bluesky provider. No kit wiring, config model or history store yet (slice 4), and no instance is named or contacted by this change.
