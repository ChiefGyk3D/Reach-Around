- `reach-around leads delete` now clears the short-lived alert hash table as part of an erasure (#905, epic #776). `--yes` requires `--alerts-database NAME`, `--alerts-database-id UUID` and `--leads-database-id UUID` (the `database_id` values from the Worker's own configuration) and fails closed (exit 2, no SQL printed) without them. Before it prints the lead SQL it asks Cloudflare for the id behind each name and refuses unless it equals the id you gave (so a decoy database with the right tables is refused), then reads both schemas, and refuses a database that lacks the `alert_dedup` table or that holds the lead tables without being the leads database. That first step exits 10: the checks passed and nothing is erased. Close the kit gate (kill switch) before you start: the tool cannot read it. After you apply the lead SQL, `--finish` reads the lead tables back for the id and for the address (a lead created again for the same address counts), checks again, clears the whole alert table with one statement that deletes only while the alert database holds no lead table, reads it back as 0, waits and reads it back again, checks the ids and schemas a last time, reads the lead tables for the address once more, and names any row whose life began after the erasure started. Every remote statement runs between two checks that the database name still resolves to the id you gave; because `wrangler d1 execute` takes a name, not an id, this binds the name to the Worker's configuration only at those moments and cannot prove which database one call used (a name re-pointed and restored inside one call is not detected). Exit 0 from `--finish` is the only completed result (a dry run also exits 0 but requests nothing); once `--finish` runs it never exits 2: exit 3 means the lead rows were read as erased but the alert hashes are not confirmed cleared, a database changed, or a lead for the address exists again; exit 4 means the lead rows are not confirmed erased. The tool runs only the wrangler installed in this repository (`--wrangler PATH` must stay inside `worker/node_modules`; never `PATH` or `npx`): the real path must stay inside the wrangler package, the package files and npm's install record must match `worker/package-lock.json`, the file and every directory above it must belong to root or you and be unwritable by others (inside the repository by group too), and the wrangler package and the dependencies it names are walked the same way (bounded; only the walked tree is checked). This is a trust boundary, not an integrity check: it hands your token to that program, never asks it for a version, and cannot prove the installed files are the published ones. It passes only the token, the account id, `HOME` and a fixed `PATH`, runs in `/` in its own process group with no shell and no stdin, reads output with a hard size cap, and kills the whole group on the cap or the time limit. The erasure guard test now records the statements the real `--finish` flow runs and judges them on the seeded schema, and the `alert_dedup` known gap is removed from `scripts/erasure-stores.json`. `docs/privacy.md`, `docs/alerts.md`, the checklist and the command help describe the steps, the exit codes and the remaining windows. The test suite can no longer start a real wrangler (directly or through an interpreter or launcher) from a Python-level process start; plain node and other tools still start where tests need them, and a child's own children are not guarded.
