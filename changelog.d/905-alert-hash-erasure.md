Before it prints the lead SQL it reads the schema of the leads database and of the named database through the repository's pinned wrangler (never found through `PATH` or `npx`; `--wrangler PATH` takes another absolute path of the pinned version that you own and others cannot write; a minimal environment, an argument list, no shell, no stdin, 120 second limit, exactly one well-formed result block per statement, integer counts only, remote text never repeated) and refuses a database that lacks the `alert_dedup` table or that holds the lead tables without being the leads database. After you apply the lead SQL, `--finish` reads the lead tables back, clears the whole alert table, reads it back as 0, waits and reads it back again, and names any row whose life began after the erasure started. Exit 0 is the only complete result; exit 3 means the lead rows are erased but the alert hashes are not confirmed cleared; exit 4 means the lead rows are not confirmed erased.
