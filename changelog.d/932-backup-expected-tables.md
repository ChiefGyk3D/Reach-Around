- The D1 backup script now keeps an inventory of the tables it expects, each with the migration that creates it (#932). It reads which migrations the database has applied: a table whose migration is applied must exist, or the run fails with the table name and exit 1 instead of ending in a successful but incomplete backup; a table whose migration is not applied is skipped with a notice. If the applied migrations cannot be read, the run fails. The two aggregate tables `view_hour_daily` and `view_city_daily` are now exported too (they were silently omitted before). A listed table name that contains a line break is refused. The script needs bash 4.0 or newer and says so. Tests derive the inventory from the migrations and fail when it drifts. A table that exists in the database but is not in the script's inventory (from a newer migration, or made by hand) now fails the run before any export, naming it; only SQLite's own `sqlite_*` tables and the reserved `_cf_KV` are accepted without an export. Every table that exists is exported whatever the migration record says: the record only decides whether a missing table is an error. The record is trusted only when it is a prefix of the repository's ordered migration list (if a migration is recorded, every earlier one is recorded too). With no migration recorded, or a record that holds a name the script does not know, a duplicate, an empty or blank name, more than 10000 rows, or a gap (a later migration recorded while an earlier one is not, as after a deleted history row), the record is not trusted and every expected table is required (a notice names at most ten entries, then the count of the rest). The record is processed in one linear pass. Table and migration names read from the database are sanitized before they are printed. The bash version guard now runs first, in POSIX syntax. The post-deploy smoke script matches the content-type and nosniff headers without a pipe into `grep -q` (which can lose a race with SIGPIPE under pipefail) and without a bash 4 expansion.
