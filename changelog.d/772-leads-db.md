- Media kit leads move to their own D1 database (#772, epic #365): leads and kit events are stored and purged only through a new `LEADS_DB` binding, with their own migration folder (`worker/leads-migrations`), so leads have separate access, backup and erasure from analytics. Every lead path (the gate, the view route and the lead purge, including a direct call to `purgeExpiredLeads`) goes through one proof in `src/kit/separation.ts` and refuses, with nothing stored and one closed log line, unless the two bindings are different databases by what each database states it is (a `db_identity` row written by its own migrations, because a D1 binding exposes no database id) and the analytics database holds no lead rows. Installations that already collected leads run the one-time, dry-run-first `scripts/move-legacy-leads.py` (copy, read back, then delete the analytics copies); `docs/deploy.md` has the steps. There is no fallback to the analytics database. The binding is only a commented block in `worker/wrangler.toml`, so no deploy creates the database early; `docs/deploy.md` says how to create it. `scripts/backup-d1.sh` with `--apply` now reads the database's own identity and refuses anything that does not say `analytics`, whatever it is called. The lead purge guarantee now starts at `QUERY_BUDGET` 12 (was 9) because the proof takes up to 3 queries. CI checks the leads migrations with no pre-rule exemption, migration number 0000 included.
