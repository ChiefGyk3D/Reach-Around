## [0.3.0-rc.7] - 2026-11-27

- Backup verifier (#962): `scripts/check-dump.py` no longer accepts a statement that starts with `DELETE FROM`. A D1 export holds a PRAGMA line, CREATE TABLE, CREATE INDEX and INSERT rows only, never a DELETE, so any DELETE now fails as an unexpected statement.
- Flaky test fix (#958): the cleanup in `tests/test_wrangler_runner_group.py` checked that the grandchild was alive and then killed it, so a grandchild that exited in between raised `ProcessLookupError`. The cleanup now tolerates a process that is already gone. No product code changed.
- Backup verifier follow-ups (#953). The notes on symbolic links now say the export file is opened with `O_NOFOLLOW` only where the platform has it. The dump check now accepts only `PRAGMA defer_foreign_keys` (what a wrangler export writes); any other PRAGMA, such as `writable_schema`, fails as an unexpected statement, and a test covers the other standalone restore statements (ATTACH, DROP, UPDATE and more). A new test proves the export is read and never run: the export passes, a stand-in SQL engine on PATH is never started, and a CREATE INDEX in the file leaves no mark in the database. Regression coverage for the monitored routes, not proof for every route. Growth during a backup stays an accepted limit: the row count proves cardinality only.
- Mastodon provider: a low or malformed rate header on an error answer now ends the read as `rate_limited` or `bad_shape` before any retry wait, instead of `server_error` or `timeout` (#950).
- Docs: the manual recovery steps for a fediverse refresh that stops with `UnitFileTooLarge` (more than 10,000 directory entries, more than 8 staged copies, or an oversized file) are in `docs/config.md`, with a test that pins them to the code constants (#945).
- The D1 backup script now checks that an export is complete (#944). A table may gain rows during the run but must not lose any: if a table's row count after the exports is below the count before, the run fails (exit 1, rerun). Each export file's rows, counted by reading it line by line without executing anything in it, must lie between the before and after counts, so an export that ends early fails the run instead of producing a short backup. The file is opened once (with `O_NOFOLLOW` where the platform has it, so a final symbolic link is refused there; on a platform without it only the regular-file check on the open descriptor and the check on the backup folder remain) and read under one byte budget shared by all the export files of the run (`BACKUP_MAX_BYTES`, default 1 GiB, a whole number up to 1 TiB, else exit 2) and a 1 MiB line limit. A NUL byte, invalid UTF-8, an unbalanced quote, several rows in one INSERT, or an INSERT or REPLACE word outside quotes anywhere but in the exact accepted statement (a CTE-prefixed insert, `INSERT OR ...`) fails the run. The row-count answer must name every exported table exactly once and nothing else, or the run fails before any export is trusted. The accepted one-INSERT-per-row grammar was verified against real D1 exports on 2026-11-27. A delete plus an insert that leaves the counts level during the run is a documented residual. Documented limit: with growth during the run the row count proves cardinality only, not that every older row is present; whether a running D1 export is one consistent snapshot is inferred, not documented. The table listing now also carries each table's definition and is taken again after the exports: a table that was dropped, added or replaced during the run fails it. A listing or count answer is trusted only when it is exactly one successful result, never an error object, several results or a failed result. The backup script's note on the ignored `_cf_KV` table now says what ignoring it means. The post-deploy smoke script now requires the content type to be exactly `text/html` (parameters allowed) and the nosniff header value to be exactly `nosniff`; values that only contain those words no longer pass.
- The instance template carries the fediverse snapshot (#942, epic #244, follow-up to #940). `scripts/refresh-counts.sh` copies the committed `numbers.fediverse.json` in for the engine and, after the run, checks the engine's copy with `scripts/validate-numbers.py --fediverse` (the engine's 512 KiB limit, required keys (`followers` and `posts` stay optional, as in the engine) and anonymity rules in standard-library Python; a symbolic link is refused and one bad part refuses the whole file, unlike the engine which drops an entry; an entry older than 30 days or dated after today is dropped, the kit's own freshness rule, so a removed source's last snapshot ages out) and a link, FIFO or folder where the engine's snapshot belongs fails the refresh before installing it as a public 0644 file ahead of `numbers.json`; the unit note, its `.bad` copy, the pending note and staged files are never carried. The `refresh-counts.yml` artifact, its file-set check (now `scripts/check-artifact.py`, tested on real trees), the second check in the publish job, the bot-branch pull request guard and `git add` now include the file, and `scripts/validate.sh` mounts it read-only beside `numbers.json` so the build feeds the kit. The egress check does not apply to the template (its refresh job has no `allowed-endpoints` list); the README says where to run `counts egress-check` if an instance adds one. Needs the workflow push scope.
- Fediverse collector slice 4, the wiring (#941 for issue #940, design in `docs/design/fediverse-collector.md`, epic #244). New config `numbers.fediverse` lists at most one Bluesky and one Mastodon-API account (`kind`, `actor` or `host` and `acct`, optional `account_id`), each checked by its provider's own validator, with no token and no unknown keys. `counts refresh` now runs the two providers once a day with the injected clock, transport and sleep: a source read in full passes the snapshot guard, is stored in `numbers.fediverse.json` beside the numbers file and appends one aggregate `api` history row per metric (`posts_30d`, `boosts_30d`, `favorites_30d`, `replies_30d`, whole numbers only); a source that is not read in full keeps its stored snapshot and the history untouched, never writes a zero, and is named in the status file by a fixed reason word. `build`, `kit pdf` and `kit private-measures` feed `kit.fediverse` from a fresh complete snapshot (labeled API, medians still worked out by the build); the hand-kept entry stays in place when there is no source, no file, a damaged or old snapshot, or an incomplete read. New command `counts egress-check` (no network) fails when a configured host is missing from a workflow's allowed-endpoints list. Documentation in `docs/config.md` and `docs/kit.md`; `docs/site.schema.json` regenerated, now with `minItems`, `uniqueItems` and length and character limits for the new source keys (the runtime-only checks are listed in `docs/config.md`). A refresh that reads a snapshot is one unit with one commit point: the snapshot is staged first, the status says `committed: false`, and the rename of the snapshot into place is the commit; the fediverse history rows are derived from the committed snapshot and written after it, then the numbers file, and the status says `committed: true` last. Every run starts by repairing what a crash left: it removes leftover staged and temp snapshot files, appends the rows a crash left out (never twice) and puts `committed: false` in a status that lags a crash; it never says `true` while an earlier attempt's pending note is live. Recovery recomputes the status from the files (no staged copy, no live note, every row of the committed snapshot in history, the numbers of the snapshot's run written) and sets a stale `true` to `false` before any repair step, so a crash during recovery cannot keep it; `true` is written only after the same check passes at the end of a run. A small unit note written before the commit point is a transaction record (the digest of the proposed snapshot, the digest of the expected numbers and a random generation id that is written back into the note once this run's numbers write landed), so a retry in which every source fails cannot report a snapshot whose numbers never landed as complete, even when the numbers bytes are the same on two days. A failed rename removes the note at once, and recovery removes the note of a transaction whose proposed snapshot is not the committed one. The rows of a committed snapshot are repaired whatever its age (a crash on one day is repaired by a run two days later); a snapshot dated after today waits and is reported with the word `snapshot_in_future`. History keeps one row set per platform, metric and day and is never rewritten: a same-day run whose values differ from that day's rows keeps the stored snapshot and reports the platform as skipped with the word `same_day_kept`. The `account_id` schema entry now bounds the integer form too (0 to 99999999999999999999). The instance template's refresh script does not carry `numbers.fediverse.json` yet; that needs a workflow change and is tracked separately. Recovery reads are bounded: the digests of the snapshot, the numbers file and every staged copy are streamed in fixed chunks and capped at the existing snapshot and numbers limits, each read asks for at most the bytes left up to the limit plus one, the folder walk that finds staged copies stops at the ninth one or after 10,000 entries and keeps nothing more, a file over its limit (or more than eight staged copies) leaves the unit pending with the fixed word `UnitFileTooLarge`, and a unit note that cannot be parsed is moved to `.numbers.json.unit.bad` (the run reports `unit_note_quarantined` and keeps the status false; the next run proceeds). `docs/config.md` documents the manual steps and the stated limit of the unit note: it gives crash consistency against this program's own crashes, not against a writer with write access to the output folder.

- The D1 backup script now keeps an inventory of the tables it expects, and every one of them is always required (#932). If the database lacks any of them the run fails before any export (exit 1), names the missing tables and tells the operator to apply the migrations first, instead of ending in a successful but incomplete backup. This is deliberate: an older schema that is not migrated yet fails rather than producing a partial copy, because a record kept inside the database (such as its migration history) can be damaged or edited and must never excuse a missing table. The script makes one read-only query (the table listing) plus the exports and no longer reads the migration history. The two aggregate tables `view_hour_daily` and `view_city_daily` are now exported too (they were silently omitted before). A listed table name that contains a line break or a carriage return is refused. A table that exists in the database but is not in the script's inventory (from a newer migration, or made by hand) now fails the run before any export, naming it; only SQLite's own `sqlite_*` tables and the reserved `_cf_KV` are accepted without an export. A test builds the schema from the migrations and fails when a migration adds a table that is missing from the inventory. Table names read from the database are sanitized before they are printed, and every list printed from the database shows at most ten names, then the count of the rest. The script needs bash 4.0 or newer and says so; the check reads the shell's own read-only version array instead of a variable an environment can set. The post-deploy smoke script matches the content-type and nosniff headers without a pipe into `grep -q` (which can lose a race with SIGPIPE under pipefail) and without a bash 4 expansion.
- Backup (#930): the table-existence check in the D1 export script no longer pipes the table list into `grep -q` under `pipefail`. That pattern could occasionally report a table that exists as missing and skip it with a "skipped" line and exit code 0; the check is now plain string matching, with a regression test that uses a table list larger than a pipe buffer.

- Fediverse collector slice 3, the Mastodon provider (#923, design in `docs/design/fediverse-collector.md`, epic #244). New `reach_around.counts.mastodon_feed` reads one public account on a Mastodon-API instance named in config, with no login: one `accounts/lookup` call (skipped when a numeric account id is configured, which then reads no follower count) and up to twelve `accounts/:id/statuses` pages of 40, built with `exclude_replies`, `exclude_reblogs` and a numeric `max_id` cursor taken from the smallest id of the previous page. The instance host must be a public lower-case ASCII DNS name (no IP literal in any notation, no local suffix, no port, userinfo, path or trailing dot, no non-ASCII spelling) and the account a plain local name; both are checked again before any request. The whole run shares one budget of 13 HTTP requests, retries and redirect hops included, and one absolute monotonic deadline of 90 seconds covering the pauses, the retry waits and every request; a response that arrives after the deadline is discarded. The walk never trusts ordering to stop early: it ends only at an empty page or when a budget ends it, so an account with more statuses than the page budget holds (12 pages of 40) reports `page_cap` incomplete by design and keeps its prior values. A `Link` header or any URL in a body is never followed. Boosts, posts by other authors, replies to other accounts and non-public posts are never counted; a malformed or unknown status makes the whole read incomplete (`bad_shape`), checked field by field through one path before any status is counted or skipped (so an old, foreign, hidden or boosted status is checked too, and a reply marker or boost marker that is present must have the right type), and an incomplete read keeps the prior rows and is never a zero. A status listed twice keeps one row with the elementwise maximum of its counts (the counts of one status only grow, so the order never matters), and copies that disagree on whether it counts end the read as `bad_shape`. A missing or malformed profile count in the lookup is `bad_shape` too, never a complete read. A missing or skewed server `Date` is `clock_skew`, a low `X-RateLimit-Remaining` is `rate_limited` and a present value that is not 1 to 10 ASCII digits is `bad_shape` (never raises); the header is checked on every response of the run (lookup, status pages, error answers and retried answers), and only a low value on the terminal empty page is let through, since no further request follows it. Every account id (the configured one, the lookup id, each status author and each reply target) must be one canonical spelling (ASCII digits, no leading zero, at most 20) and is compared as exact text, so a padded, spaced, non-ASCII, numeric or null id is `bad_shape` (or refused in config) and can never turn own posts into a complete zero. A moved or suspended account is reported and never followed. The anonymous snapshot (counts, a date, a flag and a fixed reason word; no host, account, id, text or time) passes a recursive guard and the same consistency table as the Bluesky provider. No kit wiring, config model or history store yet (slice 4), and no instance is named or contacted by this change.
- Fediverse collector slice 2, the Bluesky provider (#922, design in `docs/design/fediverse-collector.md`, epic #244). New `reach_around.counts.bluesky_feed` reads one public account on `public.api.bsky.app` with no login: one `getProfile` call and up to twelve `getAuthorFeed` pages. The whole run shares one budget of 13 HTTP requests (a retry or a redirect hop draws on it like any other request) and one absolute monotonic deadline of 90 seconds that covers the pauses between calls, the retry waits and every request's own timeout; a cursor is checked and never followed from a response, and a cursor seen earlier in the run stops the walk as incomplete. The account's own posts of the 30 days ending at the run instant, by the server's `indexedAt` and never the author-supplied `createdAt`, become rows of three whole numbers (reposts, likes, replies); reposts of other accounts, replies to others, other authors and pinned posts older than the window are not counted. The feed's order is not trusted, so nothing ends the walk early: it stops only at the end of the cursor chain (the read is complete) or at the request, page or time budget while a next cursor still exists (the read is incomplete, `page_cap` or `timeout`, and keeps the prior rows). A feed entry that cannot be read is never treated as absence: no author or a malformed one, a `reason` that is present but not a known repost or pin value (including a null or non-object one), a bad time or a bad count ends the read as incomplete with `bad_shape`. A response that arrives after the absolute deadline is discarded and the read ends as `timeout`. A snapshot is anonymous: it holds the counts, a date, a flag and a fixed reason word, and no actor, handle, DID, link, id, text or time (which account it belongs to is config; `entry_from_snapshot` takes the actor from config to build the re-check link). A read that cannot finish returns a fixed reason word (`partial_pages`, `page_cap`, `rate_limited`, `needs_token`, `account_not_found`, `clock_skew`, `bad_shape`, `timeout`, and the others on the closed list) and keeps the prior rows; a zero is only a finished empty window. The actor is validated strictly (a handle of dot-joined letter, digit and hyphen labels, or a `did:plc:` or `did:web:` id). Also added: `fetch_json_view` (the object twin of `fetch_json_array`, with the same strict numbers and header view), the guard pass over the snapshot (recursive over every key and leaf at any depth, then an exact schema and a consistency table: a complete snapshot has its rows and no reason, an incomplete one has a closed reason and either no rows or its non-empty prior rows, and every other combination is refused, also by `entry_from_snapshot` and `snapshot_aggregates`; a hit writes nothing), the window sums for the history store (`posts_30d`, `boosts_30d`, `favorites_30d`, `replies_30d`, complete reads only) and `entry_from_snapshot`, which turns a fresh complete snapshot into the same `FediverseEntry` the hand-kept `kit.fediverse` block takes; the hand-kept path is unchanged and the loader wiring is slice 4. No egress change: `public.api.bsky.app` was already on the list. A `did:web` id is accepted in its full form (a percent-encoded port and path segments) for the profile and every author, compared exactly; a post that appears twice in a run records the larger value of each count; a `reply` key that is present but null or not an object ends the read as `bad_shape`; and an account with more than about 600 feed entries in its 30-day window reports `page_cap` (incomplete, prior values kept) by design, documented in `docs/kit.md`; a feed post whose `record` is missing or not an object ends the read as `bad_shape` (no evidence it is an original post); a `did:web` host must be dot-joined DNS labels of 1 to 63 characters (no empty label, no hyphen at either end, a dot unless `localhost`) with a port of 1 to 65535 and no leading zero; and a snapshot date must be a real calendar day; a `reply` object (on the entry or on the record) only counts as a skipped reply when it has a root and a parent that each carry a well formed `at://` uri and a cid (an entry's blocked or not-found parent has no cid), and any other reply object, including `{}`, ends the read as `bad_shape`; and a counted post's uri must be an `at://` uri whose authority is the profile DID, whose collection is `app.bsky.feed.post` and whose record key is a short plain string, so a missing, malformed or foreign uri ends the read as `bad_shape` instead of keying and merging distinct posts; and a `did:plc` id must be exactly `did:plc:` plus 24 lowercase base32 characters (`a` to `z`, `2` to `7`) wherever a DID is read (the actor, the profile, every author and every uri authority), so a malformed one ends the read as `bad_shape` and never becomes a verified zero or a clean foreign-author skip. Hermetic tests only.
- Fediverse collector slice 1, the shared plumbing (#921, design in `docs/design/fediverse-collector.md`, epic #244). New `fetch_json_array` beside `fetch_json` returns a top-level JSON array with a read-only view of a few response headers (`Link`, `Retry-After`, `Date`, rate-limit headers), under a hard 1 MiB cap, with the same https, host, redirect and fixed-error-word rules; `fetch_json` is unchanged. New pure 30 day window helper (server-assigned `created_at` or `indexedAt` only, clock passed in), the aggregate-only `{boosts, favorites, replies}` row with a `NotProvided` marker so an incomplete read keeps the prior values and is never a zero, and a hand-run probe `scripts/fediverse-probe.py` that prints status codes, header names and counts only and is not run by CI. Hardening after review: `keep_prior` accepts only exact `InteractionRow` values and rejects a whole read with one bad row (`bad_shape`); the reason list is closed, including the `egress_*` words; a missing or unreadable server `Date` is treated as an untrusted clock; the array path (`fetch_json_array`) alone refuses `NaN`, `Infinity`, overflowing numbers and integers over 18 digits, while the shared object path keeps accepting numbers exactly as before; response header names are matched case-insensitively and a doubled name is dropped; unexpected transport failures map to one fixed word; the probe prints only allowlisted header names plus a count of the others; and the check that the probe is never run by CI covers `.yml` and `.yaml` workflows, composite actions, task-runner files and glob or `python -m` indirection. Second hardening round: the fixed-word fetch errors are raised after the handler is left, so they carry no chained original exception (no `__context__` or `__cause__`); on the array path the integer limit is exactly 18 digits not counting a minus sign (`MAX_INT_DIGITS`), so a 19-digit id is refused there by design and a provider that needs larger ids reads them as strings (`fetch_json` still accepts 19-digit integers such as TikTok cursors); and the probe refuses to start against the real network when a CI marker is set unless the owner override is given, with the static check also covering `find` piped to `xargs`. No provider and no live host yet; the Bluesky and Mastodon providers are #922 and #923.

- `reach-around leads delete` now clears the short-lived alert hash table as part of an erasure (#905, epic #776). `--yes` requires `--alerts-database NAME`, `--alerts-database-id UUID` and `--leads-database-id UUID` (the `database_id` values from the Worker's own configuration) and fails closed (exit 2, no SQL printed) without them. Before it prints the lead SQL it asks Cloudflare for the id behind each name and refuses unless it equals the id you gave (so a decoy database with the right tables is refused), then reads both schemas, and refuses a database that lacks the `alert_dedup` table or that holds the lead tables without being the leads database. That first step exits 10: the checks passed and nothing is erased. Close the kit gate (kill switch) before you start: the tool cannot read it. After you apply the lead SQL, `--finish` reads the lead tables back for the id and for the address (a lead created again for the same address counts, compared trimmed and lower-cased on both sides, and no wider), checks again, clears the whole alert table with one statement that deletes only while the alert database holds no lead table, reads it back as 0, waits and reads it back again, checks the ids and schemas a last time, reads the lead tables for the address once more, and names any row whose life began after the erasure started. Every remote statement runs between two checks that the database name still resolves to the id you gave; because `wrangler d1 execute` takes a name, not an id, this binds the name to the Worker's configuration only at those moments and cannot prove which database one call used (a name re-pointed and restored inside one call is not detected). Exit 0 from `--finish` is the only completed result (a dry run also exits 0 but requests nothing); once `--finish` runs it never exits 2: exit 3 means the lead rows were read as erased but the alert hashes are not confirmed cleared, a database changed, or a lead for the address exists again; exit 4 means the lead rows are not confirmed erased. The tool runs only the wrangler installed in this repository (`--wrangler PATH` must stay inside `worker/node_modules`; never `PATH` or `npx`): the real path must stay inside the wrangler package, the package files and npm's install record must match `worker/package-lock.json`, the file and every directory above it must belong to root or you and be unwritable by others and by any group another account belongs to (a group write bit is accepted only when the group is your effective primary group, lists no member but you, is no other account's primary group, and the `passwd` and `group` lines of `/etc/nsswitch.conf` name exactly `files`, which is what a normal checkout and `npm ci` give an account with its own group and umask 002; only a local files-only identity database is accepted, so with `systemd`, a directory service, an unreadable `nsswitch.conf` or any lookup error the bit is refused and the message names the alternative `chmod -R g-w worker/node_modules`; world write is refused everywhere), and the wrangler package and the dependencies it names are walked the same way (bounded; only the walked tree is checked; a symlink, to a file or a directory, must resolve inside `worker/node_modules`, the directories between its target and the repository root are checked, and a directory target is walked; a required dependency that is not installed there, or a `node_modules` in the repository root or any directory above it, is refused). Only the layout made by `cd worker && npm ci --ignore-scripts` is supported (lock file `worker/package-lock.json`, every package of the wrangler closure under `worker/node_modules`); hoisted and workspace installs are refused on purpose with a message that names that command, and a test builds that layout from the real lock file and proves it is accepted (a second test runs the resolver on a real `npm ci --ignore-scripts` install when `worker/node_modules` exists).
