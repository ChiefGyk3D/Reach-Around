# Reach Around Plan 2: Numbers Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A tagged `v0.2.0` that collects daily numbers from the easy platforms into an append-only snapshot store, tracks token health, pulls the Worker's click events into the store, and shows everything on a built-in private dashboard; then (phase 2b) two long-running listeners for Twitch viewer counts and StreamElements tips.

**Architecture:** One small collector per platform sits behind a common interface and a runner that records every run, so a failure is stored as "stale" and never as a zero. Every outbound request goes through one egress guard (public addresses only, pinned per connection) and one shared rate-limit helper. Results go into a SQL snapshot store (SQLite default, Postgres optional) that keeps every reading and resolves the day's value on read, with a checksummed, locked, transactional migration runner. A token registry tracks expiry, refreshes what it can under a compare-and-swap lease and alerts early. A static dashboard renders from the store with no JavaScript. The two listeners are separate processes that write to the same store.

**Tech Stack:** Python 3.11+, httpx and httpcore, pydantic v2, Jinja2, PyJWT with cryptography (GitHub App), openpyxl (XLSX import), psycopg 3 (optional `postgres` extra), websockets (optional `listeners` extra), pytest, ruff, mypy.

**Spec:** `docs/superpowers/specs/2026-10-23-reach-around-design.md` (sections 4.7 to 4.11, 5, 6). Roadmap: `docs/superpowers/plans/2026-10-23-roadmap.md` (phase 2 and 2b). Threat model: `docs/security/threat-model.md` (PR #54, revision 2; read it with `git show origin/docs/threat-model:docs/security/threat-model.md` until it merges). Builds on Plan 1: `docs/superpowers/plans/2026-10-23-plan-1-foundation-and-link-page.md` (`SiteConfig`, `load_yaml`, `ConfigError`, the shipped Worker in `worker/src` with table `click_events(id, ts, link_id, country)`, `ts` in epoch milliseconds, the `reach_around.cli` entry point). Platform facts come from `docs/research/*.md`; anything those notes mark UNVERIFIED is checked by the `live` test in the owning task.

## Global Constraints

- Python 3.11 or newer; tests run on 3.11, 3.12 and 3.13.
- License Apache-2.0; every new source file starts with `# SPDX-License-Identifier: Apache-2.0` (TypeScript: `// SPDX-License-Identifier: Apache-2.0`).
- American English in code, docs and messages.
- The public site is static and works with no JavaScript. The only dynamic server code is the one write-only Worker. The Worker never returns visitor data (emails, clicks, leads) through any route unless the maintainer approves the amendment in Open decision O-1.
- Do not store IP addresses. At most a two-letter country code from Cloudflare headers.
- No personal details of the maintainer (address, callsign, grid square, hostnames, machine identifiers, real emails) in the repository, examples, tests or logs. Examples use synthetic data and the placeholder callsign `N0CALL` if one is ever needed. Lease owner ids are `<pid>-<random hex>`, never a hostname.
- No secrets in the repository. Credentials come from the environment or a secrets manager.
- CI calls git-your-ship-together reusable workflows pinned by commit with a version comment: `ChiefGyk3D/git-your-ship-together/.github/workflows/python-ci.yml@8fdb8d106b11aae0f37e893bb57e9bd8e8b0e7b7 # v1.24.0`. The gate job is named `CI green`.
- Every PR links its issue (`Refs #n` or `Closes #n`). Every task has an issue and a board card before work starts.
- Versions are semantic. Tags and releases start with the first container image. While alpha, versions are `0.x`; this plan releases `v0.2.0`.
- Containers build from a `Containerfile`, run rootless as a non-root user, depend on no Docker socket, and pin base images by digest. Both `docker` and `podman` must build and run it.
- The README is marked alpha. Keep that banner until the maintainer removes it.
- Time zone for anything date-based defaults to `America/New_York`. **Every observation carries the IANA zone its `day` was computed in (`day_tz`).** Tests that touch daylight saving use these instants: local midnight is `2027-03-14T05:00:00Z` (23-hour day) and `2026-11-01T04:00:00Z` (25-hour day, ends `2026-11-02T05:00:00Z`) in `America/New_York`.
- Privacy: the site collects the bare minimum and none of it is sensitive, and says so plainly. The disclosure page and any cookie notice are generated from the features that are enabled. Plan 2 adds nothing to the public site.
- **Every outbound request goes through the egress guard (Task 22)**: https only, port 443 only, every resolved address public, resolution pinned to the connection, every redirect revalidated. No collector builds its own `httpx.Client`.
- **Every collector request goes through `request_json` and the shared rate-limit helper (Task 23).** A guard test fails when a platform module calls an HTTP client directly.
- **Collectors never log or persist secrets or the Kick stream key.** Tokens, keys, webhook URLs and DSN passwords appear in no log line, exception message, database row, dashboard or alert.
- **A collector failure is recorded as stale, never as zero.** A missing field, an empty response or an error writes no observation and records a failed run. A value computed from a truncated listing carries `coverage = partial` or is not written.
- **Imported and typed values are flagged as such** (`source` is `imported` or `typed`) everywhere they are stored and shown.
- **Observations are append-only**: no code updates a stored observation, and the only delete is `Store.purge_expired` for owner-authorized rows past their `expires_at`. Corrections are new rows. Reads resolve one value per day (Task 2): a *snapshot* is a reading at an instant and the latest reading of an open day wins; an *aggregate* is a closed-day total, written only after its day completes, and may be revised only inside a short settle window, after which it is sealed.
- **Every observation carries an origin tag** (`public_api`, `owner_authorized_api`, `imported`, `typed`) so the phase 5 display-policy check can refuse a forbidden field on a public page. The `access` column records how the data was authorized, not who may see it; audiences (public, gated partner, owner-only) are decided by the phase 5 policy, and until it exists every number is treated as owner-only. Public counts are kept until a platform's terms say otherwise; owner-authorized data may carry an `expires_at` (platform retention terms, for example YouTube Analytics 30 days) and is purged when it passes.
- **The collector host holds the one credential able to read the Worker's data, and the pull asks only for aggregates**: grouped counts, never rows, never the leads table. Lead emails never enter an aggregate table, the kv table, a log or an export. Which credential that is stays open until Open decision O-1 is answered.
- **Refresh tokens rotate under a lease** (Task 4): one holder at a time, compare-and-swap on row counts, the rotated access and refresh tokens replaced in one atomic write, a generation number that proves who refreshed last.
- **Migrations are locked, checksummed and transactional** (Task 2): a shipped migration is never edited, the engine refuses a database newer than itself, and there are no down migrations.
- Secret files and databases are created owner-only: files mode 0600, their directory 0700.
- Dependencies are pinned with hashes; regenerate the lockfiles Plan 1 created whenever a task adds one.

## Open decisions for the maintainer

The plan proceeds on the stated default for each so work is not blocked, but none of these is decided. Each lists options and trade-offs, not a recommendation.

**O-1. How does the collector host read click aggregates from the Worker's database?** (Task 16S answers part of this with evidence; Task 16F is built only if option B is chosen.)

| Option | What it is | For | Against |
|---|---|---|---|
| A. Read-only D1 token (Task 16, default) | A Cloudflare API token limited to reading D1 runs two fixed grouped statements | No Worker change; no spec amendment; spec 4.4 and 4.11 already describe this | Task 16S must prove the token cannot write; if it can also read `leads`, the collector host holds a token that reads every lead email (threat model F12) and the maintainer must accept or restrict it by network source and rotation; the D1 REST API has no per-table scope |
| B. Signed owner route in the Worker (Task 16F) | `GET /e/o/clicks` returns grouped counts only for an HMAC-signed owner request | No Cloudflare API token on the collector host; the credential reaches only counts; works if A fails the spike | Amends spec 4.4 ("never returns visitor data") and 4.11; adds a read route and a nonce table to the one component that faces the internet; the signing key becomes a new high-value secret (rotation by `kid`); more Worker code to audit and to pay per request |
| C. Worker writes a daily aggregate object that the host reads | A Worker cron writes counts-only JSON to R2 or KV; the host reads it with a read token | The host token cannot reach D1 or leads at all; no read route | Needs R2 (account setup, possibly a payment method) or KV (read tokens are account-wide, so they could also read the gated bundle namespace); whether R2 tokens can be scoped to one bucket is UNVERIFIED; one more moving part and a daily cron in the Worker |
| D. Owner-run export, no standing credential | The owner runs a local command (their own interactive login) that exports counts to a file; `pull-events --from-file` ingests it | No credential stored anywhere on a server | Not unattended; a missed day waits for a human; the cursor and dead-letter logic still apply |

Task 16 is written against an `AggregateSource` interface, so the window, validation, dead-letter and cursor logic is the same for every option; only the transport module differs. Config `worker_events.transport` takes `d1`, `signed_worker` or `file`; option C would add a fourth.

**O-2. YouTube in v0.2.0?** The spec's first-release table lists YouTube as "public counts with a key; OAuth for owner analytics", and the roadmap puts it in phase 5. The plan defers it (Task 24 is a stub) because the research note says public counts read without owner authorization may be stored for 30 days at most, which conflicts with "the store is the history", and because the display-policy table (phase 5) must exist before any YouTube figure can reach a page. Options: (1) defer to phase 5 as planned (about 0 extra hours now); (2) build a public-key subscriber, view and video count collector now with a 30-day `expires_at` on every row, which means Task 2 must allow `expires_at` on public rows and the history for YouTube is then a rolling 30 days (about 10 more hours); (3) build it now without the cap and accept the policy risk (not recommended by the research note). Ask YouTube API compliance staff (research question 4) before choosing 2 or 3.

**O-3. Where do scheduled collectors run?** Spec 4.11 lets public-endpoint collectors run as scheduled CI jobs. Because CI has no persistent disk, that needs a Postgres store the CI runner can reach, which means a hosted database with its DSN in CI secrets (threat model T-19). Options: homelab container only (no hosted database; CI runs nothing); hosted Postgres reachable from CI (more convenience, a new exposed credential and cost); CI job that uploads a SQLite file as an artifact the homelab merges (no inbound database, more code). The plan documents the first two and builds neither beyond the `dsn_env` support in Task 3.

**O-4. Click storage shape.** Threat model D-05 proposes aggregating on write in the Worker (bounded storage). Task 16's id cursor assumes raw rows with ever-increasing ids (Task 16 adds an `AUTOINCREMENT` migration to make that true). If D-05 is accepted, the pull must read closed hourly aggregates instead and Task 16's cursor logic is replaced by a closed-hour read; about 6 more hours.

**O-5. Token rotation intervals and owner role (threat model D-14).** The registry requires an owner role, a scope list and a revocation step for every credential and alerts on overdue rotation. The default interval is 90 days for credentials the owner mints and "at consent expiry" for OAuth. Options: keep 90; choose per credential; allow `null` (no scheduled rotation, provider expiry only).

**O-6. Poisoned click window.** A window whose aggregates fail validation is rejected whole and retried (Task 16). Options for a window that stays bad: keep alerting until the owner fixes the source (default); allow `pull-events --skip-window LO HI` with a recorded reason (counts for that range are lost, forever, and shown as a gap); skip automatically after N days (never silent loss is violated, so not offered).

**O-7. Which reading is "the day's value" for a snapshot?** The first draft kept the first reading of a day and refused later ones. This revision keeps every reading and returns the latest reading of an open day, then freezes the day when it closes. Options: latest reading wins (default; matches an end-of-day count and lets a corrected reading replace a bad one); first reading wins (a stable morning value; cannot be corrected); one fixed time of day (needs the scheduler to be exact). The spec's wording, "one row per platform, account, metric and day", holds for reads; storage keeps the revisions.

**O-8. Settle window for closed-day aggregates.** Aggregates (GitHub traffic days, Twitch stream minutes, tips) may be revised for 3 local days after the day closes, to take in late-arriving VODs and late tips, and are then sealed; later changes are refused and counted. Options: 3 days (default); 1 day; per-collector values; never seal.

**O-9. Kick live status and viewers.** Spec section 5 lists them; Plan 2 collects Kick subscribers only because a viewer figure needs a sampler like Task 19. Options: add a Kick sampler to phase 2b (about 12 hours), defer to a later phase, or drop.

**O-10. Patreon has no roadmap work package.** The spec lists Patreon (official v2 API, patron counts) but neither the roadmap nor this plan schedules it. Options: add a phase 5 package, add it to this plan (about 10 hours), or drop it.

## Review Focus

Failure modes the spec implies but no obvious test covers, most likely first. Each has a test in the task that owns the code.

1. **Failure written as zero, or a truncated listing written as a total.** An HTTP 500, an empty body, a missing or non-integer count field, a Twitch listing cut off by a page failure or a page cap, or a bot account removed from a room must produce a failed or partial run and no complete observation; the dashboard shows "stale since" with the last real value, never 0. A day with no VOD is a gap, not a zero. (Tasks 6, 8, 12, 13, 17)
2. **Kick stream key leak.** `stream.key` must not reach any log level, exception text, database table or dashboard, including on the error path. A sentinel value is searched for everywhere. (Task 14)
3. **Lost, raced or half-written refresh credentials.** A single-use refresh token rotated but not persisted, refreshed twice by two processes, written without its matching access token, or orphaned by a holder killed between the provider call and the write, locks the owner out until a manual login. Tests run real processes and kill them at each step. (Tasks 4, 12, 13)
4. **Wrong day.** A reading or aggregate placed on the wrong local day at a daylight-saving change, a closed day silently rewritten, a late VOD or tip lost, or a mixed-zone history. (Tasks 2, 7, 10, 13, 15, 20)
5. **Event pull loses or doubles counts.** A malformed bucket skipped while the cursor advances loses events for good; a retried window or two concurrent pullers double counts; a reused Worker id skips events. The whole window is rejected, dead-lettered and retried, and the cursor moves only by compare-and-swap. (Task 16)
6. **Server-side request forgery.** A user-supplied Mastodon or Matrix host, a redirect, or a DNS answer that changes between check and connect reaches a private, link-local or metadata address. (Tasks 5, 9, 12, 22)
7. **Migration half-applied.** A crash, a second process or an edited shipped file leaves the schema in a state the next start cannot detect. (Tasks 2, 3, 4, 19, 20)
8. **Partial or repeated data frozen into history, and hostile import files.** An incomplete current day stored as final; a CSV or XLSX with NaN, negative or future values, duplicate rows, formula cells, a zip bomb, a symlink or FIFO path, or one bad row among a thousand good ones is rejected whole, with row numbers, and writes nothing. (Tasks 10, 13, 15)
9. **Rate-limit handling that hammers.** Sleeping a capped time and retrying when the server said to wait hours; ignoring a reset header; two processes sharing one quota with no memory of each other. (Tasks 13, 19, 23)
10. **A read path that widens the Worker's blast radius.** Whatever option O-1 selects must leave the collector host unable to write, and unable to read leads if avoidable. (Tasks 16S, 16, 16F)

Adding a collector or a command never edits a shared file: `collectors.base.discover()` imports every module in `collectors/platforms/`, and `cli.main` imports every module in `commands/` and calls its `register(subparsers)`. This is what lets the platform tasks run in parallel.

Shared test helpers (created in Task 6, `tests/collectors/conftest.py`): fixture `ctx` builds a `CollectorContext` with an `httpx.MockTransport` whose handler the test sets, an in-memory `SqliteStore`, `EnvSecrets` over a dict, `now=datetime(2026, 10, 23, 14, 0, tzinfo=UTC)`, a recording `sleep`, and a gate whose clock the test controls; `ctx.tz_for(account)` returns the account's zone (default `America/New_York`). Fixture `captured_logs` captures all `reach_around`, `httpx` and `httpcore` records at DEBUG.

`tests/mp.py` (created in Task 2) gives every multi-process test the same tools: `run_children(target, n, *args)` using the `spawn` start method, `Barrier`-style release through a file, and `kill_at(point)` which makes the child call `os._exit(137)` when it reaches a named hook point. Production code exposes no such hook: the tests wrap the public seams (`Db.execute`, `SecretBackend.set_many_if`, the refresher callable) inside the child.

- **Migration rules** (`store/migrate.py`, shared by both adapters):
  1. Files `migrations/NNNN_name.sql`; `NNNN` unique; gaps allowed; applied strictly in order. Applied versions are recorded in `schema_migrations(version PRIMARY KEY, name, checksum, applied_at)`; the checksum is SHA-256 of the file bytes with `\r\n` normalized to `\n`.
  2. `migrate()` takes `Db.migration_lock()` for its whole run, so a second process waits and then finds nothing to do.
  3. Every pending file runs in its own transaction together with its `schema_migrations` row, one statement at a time (the shared splitter uses `sqlite3.complete_statement`; migrations may contain only plain statements, no `;` inside a string or trigger body). A failure rolls the transaction back: no partial table, no row.
  4. **Immutable:** if an applied version's file is missing or its checksum differs, `StoreError("migration 0002 changed after it was applied")` names the file and never prints content.
  5. **Downgrade policy:** if the database holds a version the code does not know, `StoreError` says the database is newer than this build and to upgrade the engine or restore a backup. There are no down migrations. A SQLite store with pending migrations is copied first (`VACUUM INTO`, mode 0600, `<name>.pre-<version>`; the three newest copies are kept); for Postgres the docs name `pg_dump`.
  6. **Order:** a file with a version lower than the highest applied version that is not itself applied is refused (`StoreError("migration 0003 is older than applied 0004")`). Numbers are claimed in merge order; a branch renumbers on rebase.
  7. CLI `reach-around store status|migrate --config PATH` prints applied and pending versions and runs `migrate()`.

- Refresh algorithm (this is the behavior the tests pin):
  1. `acquire_lease`: `UPDATE tokens SET lease_owner = ?, lease_until = ? WHERE name = ? AND (lease_owner IS NULL OR lease_until < ?)`; row count `1` wins. A loser polls every 250 ms for up to 30 s (injected `sleep`); on each poll it re-reads `generation` and, if it is greater than `seen_generation`, returns `RefreshOutcome(False, generation)` without calling the refresher. Timeout raises `LeaseTimeout`.
  2. After winning, re-read `generation` and run `reconcile`: the secrets backend stores `__ra_meta__:<name>` (JSON: `generation`, both expiries) in the same atomic write as the tokens. If the stored generation is higher than the registry's, a previous holder wrote the secrets and died before committing; adopt it (a compare-and-swap on `generation`) and return `refreshed=False` without calling the provider.
  3. Call `refresher(current_secrets)` once with the values read inside the lease. The HTTP timeout of a refresher (20 s, never retried) must be under half the lease ttl; `refresh` asserts it.
  4. `set_many_if({tokens..., meta(generation+1)}, guard={meta key: meta(generation)})`, then read back and compare. A `False` return means a newer generation already exists: discard, return `refreshed=False`. A raised error sets `needs_attention = "write_failed"` (a compare-and-swap on the lease owner), releases the lease and re-raises.
  5. Commit: `UPDATE tokens SET generation = generation + 1, access_expires_at = ?, credential_expires_at = ?, last_refreshed_at = ?, needs_attention = NULL, lease_owner = NULL, lease_until = NULL WHERE name = ? AND lease_owner = ? AND generation = ?`. Row count `0` means the lease was lost after the secrets were written: run `reconcile`, which adopts the written generation.
  6. `RefreshRejected` from the refresher sets `needs_attention = "invalid_grant"`, emits a `compromise_suspected` alert (never "expired"), releases the lease and re-raises. The runbook step is to remove the app's grant at the provider and re-consent.
  7. A holder killed after the provider rotated the token but before the secrets write has lost the only valid refresh token; the next refresh gets `invalid_grant` and takes path 6. This is stated in `docs/education/token-health.md`, not hidden.
- Migration `0002_tokens.sql`: `tokens(name PK, platform, account, owner, scopes, revocation, rotation_days, secret_names, credential_expires_at, access_expires_at, refreshable, generation INTEGER NOT NULL DEFAULT 0, last_refreshed_at, needs_attention, last_threshold, last_alert_day, lease_owner, lease_until)`. Scope names, never values; no secret value is ever a column.

For each id window `(lo, hi]` from the cursor up to `upto`, with `hi - lo <= min(window, source.max_span)`: fetch, `validate_window`, convert, and call `store.apply_click_batch(rows, lo=lo, hi=hi, source_total=agg.total)`. A `False` return means another puller moved the cursor: stop quietly with `cursor_moved = True`.
    3. A `WindowRejected` records a dead letter for `(lo, hi)` with the reason, increments its attempts, **does not advance the cursor and does not fetch later windows**, records a failed run for platform `reach-around-worker`, account `clicks`, and dispatches one `pull` alert per day. A transport error (`HttpError`, `QuotaExhausted`) records a failed run and no dead letter. A later success on a window with an open dead letter resolves it as `applied`.
    4. On success records an ok run.
  - `FileSource(path)` (option D): reads an exported JSON file in the same shape and applies the same validation.
  - CLI `reach-around pull-events --config PATH` and `reach-around pull-events --skip-window LO HI --reason TEXT --yes-lose-events`: the skip applies only to an open dead letter whose `lo` equals the cursor, records the skip with the reason, moves the cursor, and prints that the range is lost (Open decision O-6). **Interfaces:**
- Consumes: `AggregateSource`, `ClickBucket`, `WindowAggregate` (Task 16), `click_events` (Plan 1 Task 8, after the Task 16 migration).
- Worker secret `OWNER_SIGNING_KEYS`: JSON `{"active": "<kid>", "keys": {"<kid>": "<base64 key, 32 bytes>", ...}}` with at most two keys (the active one and the previous one). More than two, invalid JSON, a key under 32 bytes, or a missing secret disables the route entirely.
- Request: `GET /e/o/clicks?after=<id>&upto=<id>` with headers `X-RA-Kid`, `X-RA-Timestamp` (epoch seconds), `X-RA-Nonce` (32 hex characters), `X-RA-Signature` = hex HMAC-SHA256 over `RA1\nGET\n/e/o/clicks\n<kid>\n<query sorted by name>\n<timestamp>\n<nonce>`. The kid is inside the signed text, so it cannot be swapped.
- Bounds, all enforced by the Worker: `after` and `upto` are decimal integers; `0 <= after < upto <= current max id`; `upto - after <= 5000`; timestamp within 60 seconds of the Worker's clock; the response holds at most 5,000 buckets, which can never be exceeded because a bucket needs at least one row and the span is capped at 5,000 rows; the body is under 256 KiB; the response has `Cache-Control: no-store`.
- Response: `{"max_id": n, "total": n, "buckets": [{"bucket_ms", "link_id", "country", "count"}]}` and nothing else. It is built from two fixed statements over `click_events`; no other table is read except `owner_nonces`.
- Order of checks (cheap first, so unsigned traffic never touches D1): method and path, feature enabled, header shape, timestamp window, kid lookup, constant-time signature check (`crypto.subtle.verify`), rate limit keyed by kid (only correctly signed requests count against it, so an attacker without a key cannot lock the owner out), atomic nonce insert, range bounds, queries. **Every failure at any step returns the same empty 204 the Worker gives every other path**, so the route's existence is not revealed (the first draft said 404, which no other path returns).
- Atomic nonce: `INSERT INTO owner_nonces (nonce, expires_at) VALUES (?, ?)` with `nonce` as the primary key; a request proceeds only if the insert succeeds (`meta.changes == 1`) and a unique violation means replay. There is no check-then-insert. Nonces live 180 seconds and are pruned by the daily cron and opportunistically on insert.
- Python: `SignedWorkerClient(worker_url: str, signing_key: str, kid: str, http: httpx.Client)` implements `AggregateSource` with `max_span = 5000`; a 204 is reported as "owner route refused the request (signature, range, clock or limit)", never as zero events; the worker host goes through the egress guard.
- Disclosure scope (documented in `docs/education/system-of-record.md` and proposed for the threat model): a holder of a valid key can learn, per 15-minute bucket, how many clicks each link and country received, and the highest event id and the row count of a range. It cannot learn lead data, emails, addresses, user agents, individual event times, or gated content. Compromise of the key lets an attacker read those counts, spend the rate limit (six requests per 60 seconds per kid) and add nonce rows at that rate. It does not let them write click events, read leads or unlock a kit; the key is separate from the kit signing key and from the Cloudflare API tokens.
