# Reach Around Plan 4: Analytics Funnel Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Before the real-hostname cutover, the link page's analytics are at least as useful as Beacons: where visitors come from (referrer host or `utm_source`), what they view (page), where they go (link, support route, copy or QR action), and who they are in coarse terms (country, region, city, browser family and major version, OS family, device class, language, window size class, network type), with traffic split into likely-human and automated so the numbers can be trusted. Nothing is stored that identifies a person: no IP address, no user agent string, no full referrer, no cookie, no browser storage.

**Architecture:** A new static script (`view.js`, `script-src 'self'`) sends one `navigator.sendBeacon` per page load to a write-only Worker route `POST /e/v/:pageId` carrying only the referrer host, an allowlisted `utm_source` and a window-size letter; it sends nothing at all when Global Privacy Control or Do Not Track is on. The Worker, in memory and at write time, reads the connection address and the `User-Agent` and `Accept-Language` headers and Cloudflare's request metadata, derives small categories from them (browser, OS, device, language, network type, bot class and reason, geography), and discards the raw values before the first database call. It stores one raw row per view for a short window and a daily keyed hash of the address (current UTC day only) to count unique visitors. A daily Worker job rolls closed days into three capped aggregate tables, one marginal table per kind of fact, never a wide per-visitor row, and then purges raw rows. The Plan 2 collector pulls the closed-day aggregates through the same transport it chose for clicks (Plan 2 Open decision O-1), validates them whole-window, stores them in the local snapshot store, and the built-in dashboard and Grafana read the funnel from there. Network-type and crawler verification use a compact range dataset consulted inside the Worker (KV plus an in-isolate cache); no visitor address ever leaves the Worker.

**Tech Stack:** TypeScript Cloudflare Worker, D1, KV, Workers Rate Limiting binding, Web Crypto, vitest; Python 3.11+, pydantic v2, Jinja2, pytest, ruff, mypy; plain ES5-style browser script.

**Spec:** `docs/superpowers/specs/2026-10-23-reach-around-design.md` (sections 4.4 `event`, 4.10, 4.11, 6). Roadmap: `docs/superpowers/plans/2026-10-23-roadmap.md` (not edited here). Threat model: `docs/security/threat-model.md` (T-05, T-07, T-12, T-17, F3, F15, F16, D-04, D-05). Builds on Plan 1 (`handleClick`, `click_events`, `purgeOldEvents`, `click.js`, `ping` attributes, `_headers`/CSP, `collected_items`, `Features`), Plan 2 (Tasks 2, 6, 16/16S/16F, 17 and Open decision O-1) and Plan 3 (Tasks 16, 17, 18: body cap and kill switch, route budgets, bounded logs). Issue: ChiefGyk3D/Reach-Around#101; related #82 (support hub).

Plan task ids here are `A0` to `A20` so they never clash with the numbered tasks of Plans 1 to 3.

## Decided by the maintainer (not open)

1. **No raw IP address is stored or logged, ever.** The address and the raw `User-Agent` may be read and processed transiently in memory at write time to derive coarse facts. They are never stored, logged, put in an error message or sent anywhere. Only the derived categories are stored.
2. **Basic data only, kept low-sensitivity and minimal:** path (page), referrer host, time, and the derived categories listed in "Dimensions" below. No cookies, no `localStorage`/`sessionStorage`/IndexedDB, no fingerprinting, Global Privacy Control and Do Not Track honored (nothing sent, nothing recorded).
3. **Funnel = source, then page, then click.**
4. **Cutover of the real hostname waits for this.**
5. **Geography: country, region and city are all stored** (city ON). Never coordinates, postal code, metro code or any finer location. The privacy text says this plainly.
6. **Bots are counted in a separate bucket, not dropped.** Config keeps an option to drop them (`analytics.bots: count | drop`, default `count`). Nothing extra is stored about bot traffic.
7. **Unique visitors: yes**, a daily-rotating keyed hash of the connection address, held only for the current UTC day and deleted by the daily job.
8. **Network type includes VPN, proxy, Tor and hosting detection**, with lookups done locally. A visitor address is never sent to any third-party API or service.
9. Local-first hardware and the repo rules stand: Apache-2.0, American English, synthetic data only, no personal details in the repo.

## Global Constraints

Copied from Plans 1 to 3, then extended. Where Plans 1 to 3 say "at most a two-letter country code", decision 5 supersedes it for page views only; click rows keep country only. The amendments this needs are listed in "Conflicts with existing documents".

- Python 3.11 or newer (tests on 3.11, 3.12, 3.13). Every new source file starts with an SPDX line (`# SPDX-License-Identifier: Apache-2.0`, TypeScript `// SPDX-License-Identifier: Apache-2.0`). American English.
- The public site is static and works with no JavaScript. `view.js` is progressive enhancement; the page, links and `ping` clicks work without it.
- The Worker never returns visitor data. Every outcome of `/e/v/*` is the same empty 204 with the same headers.
- **No cookie, no `localStorage`, `sessionStorage`, IndexedDB or Cache API in any shipped script. No canvas, WebGL, audio, font, battery, plugin, screen-size, pixel-ratio or client-hint reading.** The only environment value the script reads is `window.innerWidth`, and only to pick one of four size letters.
- **The raw address and raw `User-Agent` are locals of one function.** They are not returned from it, not passed to any logger, not interpolated into any string that reaches `console`, an `Error` message, a D1 bind or a KV key. Only enums leave the function.
- **No request-derived value is logged.** Plan 3 Task 18's `logEvent` (closed enums) is the only logger. New events `pv`, `rollup`, `net` are added to its closed set.
- **No third-party call with visitor data.** During a request the Worker uses only its own D1, KV and rate-limit bindings. A test fails if `fetch` is called in a request path.
- Cloudflare fields: free-plan fields only (`request.cf.country`, `regionCode`, `city`, `asn`, `httpProtocol`, `tlsVersion`, plus the `CF-IPCountry` and `CF-Connecting-IP` headers). Bot Management fields (`botManagement`, `verifiedBotCategory`, JA3/JA4) are never read unless the flag `CF_BOT_MGMT=1` is set, and are never stored. Which fields exist on the maintainer's plan is verified by Task A0, not assumed.
- Never read or store `asOrganization`, `latitude`, `longitude`, `postalCode`, `metroCode`, `timezone` as a location, the ASN number, or any TLS fingerprint. A guard test scans `worker/src` for these names.
- Third-party range data is never vendored unless its license is read and recorded in `docs/research/network-datasets.md` (Task A16). The default for everything unread is fetch at refresh time into the owner's KV, never committed.
- Every PR links its issue (`Refs #101` or `Closes #101`). CI calls the git-your-ship-together workflows; the gate job is `CI green`. Versions are semantic; alpha is `0.x`; the README stays marked alpha.
- Time zone for anything day-based defaults to `America/New_York` (`SiteConfig.timezone`). Test instants for daylight saving: local midnight is `2027-03-14T05:00:00Z` (23-hour day) and `2026-11-01T04:00:00Z` (25-hour day, ends `2026-11-02T05:00:00Z`).
- Synthetic data only: addresses `198.51.100.7`, `203.0.113.9`, `2001:db8::7`; ASN `64500` (documentation range); hosts `*.example.test`; organization `Example Hosting Ltd`.

## Design reference

### Data flow and what is stored where

| Where | What | Lifetime |
|---|---|---|
| Worker memory, one request | raw address, raw `User-Agent`, `Accept-Language`, `request.cf` values, ASN number | microseconds; never leaves the handler |
| D1 `view_events` (raw, one row per accepted view) | minute-rounded `ts`, page id, source kind and value, country, region, city, browser family, browser major number, OS family, device class, language subtag, window-size letter, network type, bot class, bot reason, `first` flag | `analytics.raw_keep_days` (default 7), only after its day is rolled up, hard maximum 90 |
| D1 `visitor_seen` (day, hash) | the daily keyed hash, humans only | current UTC day; deleted by the daily job (at most about 24 h 5 min after first write) |
| D1 `view_daily`, `view_dim_daily`, `view_geo_daily` | closed-day aggregates, three marginal tables, capped | 90 days (existing schedule), by then pulled into the local store |
| D1 `view_rollup_log`, `view_meta` | per-day totals for reconciliation; `rolled_through`, heartbeat, dataset status | 90 days / permanent (tiny) |
| KV `net/v1` (and `net/stage/<source>`) | compact CIDR ranges with a class byte: no visitor data | replaced at each refresh |
| Local store (Plan 2) `view_daily`, `view_dim_daily`, `view_geo_daily`, `link_pages` | the same aggregates, pulled | the store is the history (spec 4.11) |

The three aggregate tables are deliberately separate. A day's browser totals, OS totals, language totals and city totals are stored as independent marginals, never as one row that combines browser, OS, language, window size and city. The raw row does combine them, which is why it lives for days, is never pulled, and is deleted after rollup. The aggregate side cannot be recombined into a per-visitor profile.

### Dimensions: what is stored, and why it is coarse enough

Entropy figures are rough estimates from general knowledge, not measurements; the point is the ordering and the controls, not the decimals.

| Dimension | Stored value | Rough entropy | Fingerprinting risk and control |
|---|---|---|---|
| Referrer host | host only, lowercased, no `www.`, no port; top N (default 20) plus `other` per day | high if free text, so the host charset is strict | full URL, path, query and fragment never leave the browser; IP-literal and single-label hosts rejected; cap bounds attacker-supplied cardinality |
| `utm_source` | `[a-z0-9-]{1,30}`; shares the top-N with the referrer | attacker-chosen label | charset cannot carry an email or URL; cap |
| Country | two letters | about 4 bits | coarse; kept always |
| Region | ISO 3166-2 subdivision code, 1 to 3 characters | about 5 to 6 bits | a (day, region) with fewer than 5 views is folded into the country |
| City | Cloudflare's city name, NFC, letters/marks/space/hyphen/apostrophe/period, 60 characters max | about 8 to 12 bits | highest-risk field, kept by the maintainer's decision; (day, city) with fewer than 5 views is folded into the region; raw rows holding small-town cities live 7 days at most; never joined to browser, OS or language in any aggregate |
| Browser | family enum (`chrome edge firefox safari opera samsung other`) plus integer major version | about 2 bits plus 2 to 3 bits | exact version never stored (`128`, not `128.0.6613.84`); the value is a marginal only; cap |
| OS | family enum (`windows macos linux android ios chromeos other`) | about 2 bits | marginal only |
| Device class | `mobile tablet desktop other` | about 1 bit | iPadOS desktop-mode Safari reports as `desktop`; documented limitation |
| Language | first `Accept-Language` primary subtag (2 to 3 letters); top 15 plus `other` per day | about 3 bits | marginal only; cap; the full header, quality values and region subtags are not stored |
| Window size | one letter: `s` under 480, `m` 480 to 767, `l` 768 to 1199, `x` 1200 and up | 2 bits | the browser sends the letter, not the number |
| Network type | `residential mobile vpn-proxy hosting-datacenter tor unknown` | about 2 bits | never the ASN, never the organization name; the dashboard labels it "likely" |
| Bot class and reason | class `h v a s`, reason from a closed list | low | derived from the other facts; the bucket is the only extra stored about a bot |

Together the raw row would be close to a fingerprint (city, browser, OS, language, size). Three controls keep that bounded: no identifier is stored beside it (the daily hash is in another table with no join key), raw rows live days not months, and every aggregate is a single-dimension marginal with small-count folding.

### Bot classes and reason codes

| Class | Code | Meaning | Reasons (closed list) |
|---|---|---|---|
| human-likely | `h` | nothing suspicious found | `ok` |
| verified-crawler | `v` | a search engine whose claim is checked against the vendor's published ranges, or a link-preview fetcher that declares itself | `se_verified`, `prev_declared` |
| automated | `a` | declares itself a bot, headless browser or scripted client, or has no `User-Agent` | `ua_bot`, `ua_headless`, `ua_script`, `ua_none` |
| suspicious | `s` | looks like a browser but fails a consistency check | `crawler_spoof`, `net_dc`, `no_lang`, `no_sec_fetch`, `hdr_combo`, `tls_old`, `rate`, `no_view` |

Rules, first match wins: declared search-engine UA with its address in that vendor's published ranges is `v/se_verified`; a declared search-engine UA outside them is `s/crawler_spoof`; a declared search engine when the dataset is unavailable is `a/ua_bot` (a claim that cannot be checked is not called verified); a declared preview fetcher is `v/prev_declared`; a headless, scripted or generic bot UA is `a/...`; a missing UA is `a/ua_none`; otherwise any one weak signal gives `s/<reason>` (first in the order `net_dc`, `no_lang`, `no_sec_fetch`, `hdr_combo`, `tls_old`, `rate`); no signal gives `h/ok`. A VPN, proxy or Tor address alone is never a signal (people use them); a hosting or datacenter address with a browser UA is, and the dashboard says so. Click-side only: `no_view` (a click from an address with no view hash today, humans only, and only when uniques are on) is a weak signal that counts toward `s` only together with another one, because JS-off and blocked-script visitors are legitimate.

Honest limits, repeated on the dashboard: Pages serves the HTML itself, so a crawler that never runs JavaScript never reaches the Worker and is not in any count here; the split covers clients that ran `view.js`. Declared crawlers that render JavaScript (some search engines) do appear. Everything is "likely", not proof.

### Network-type dataset (local lookup)

Inputs: Cloudflare's `request.cf.asn` (free, read transiently) mapped by two small hand-authored ASN lists (`hosting`, `mobile`, compiled from the cloud providers' and carriers' own published ASN numbers, which are facts), and a compact range blob in KV for what an ASN cannot tell: hosting/cloud ranges, community VPN/proxy ranges, the Tor exit list, and the search engines' published crawler ranges.

Resolution order: Tor range, then crawler range (returns the vendor), then VPN/proxy range, then hosting range, then hosting ASN, then mobile ASN, then `residential` if an ASN was present, else `unknown`. `residential` means only "no list matched", and the dashboard says "likely residential".

Blob format `net/v1` (little-endian, 4-byte aligned, one KV value): magic `RAN1`, version u32, built-at u32 (epoch seconds), counts (v4 ranges, v6 ranges), then `u32[] v4Start`, `u32[] v4End`, `u8[] v4Class` (padded), then IPv6 as the first 64 bits split into `u32[] v6StartHi, v6StartLo, v6EndHi, v6EndLo` and `u8[] v6Class`. Sorted by start, non-overlapping (overlaps resolved at build by class priority). Class bytes: 1 hosting, 2 vpn-proxy, 3 tor, 16 google crawler, 17 bing crawler, 18 apple crawler, 19 duckduckgo crawler. Size estimate: roughly 60,000 IPv4 and 10,000 IPv6 ranges is about 0.7 MB, far below the KV value limit; none of it is bundled in the script, so the script-size limit is untouched.

Performance design: the isolate loads the blob at most once an hour (`KV.get(key, {type: "arrayBuffer", cacheTtl: 3600})`), keeps typed-array views over it in module scope, and does a binary search of at most 17 steps per lookup, microseconds of CPU. The first request in a cold isolate races the KV read against a 150 ms timer; on timeout or any error the class is `unknown` and the load continues in the background. At most one KV read per isolate per hour keeps reads far under the free daily allowance even with many isolates (the plan's figures for Workers and KV limits are the maintainer's to verify and are listed under NOT VERIFIED). The alternative, a D1 range table queried per request, costs a D1 read per view and a round trip on the hot path, and is rejected for the same reason Plan 3 avoids D1 on the hot path.

Fail safe: missing key, bad magic, wrong version, truncated buffer, counts that do not match the length, unsorted starts, or any thrown error all give `unknown` for the network type and `null` for the crawler vendor, record `view_meta('net_status')`, emit one `net` log event per minute at most, and never change the response or block the request.

Refresh: weekly (a second cron trigger). Each source is fetched by fixed https URL constants from `worker/src/net/sources.ts` (no URL is ever built from a request), with a 10 second timeout, an 8 MiB cap, no redirects followed to another host, a range-count window and sanity rules (no prefix shorter than /8 for IPv4 or /19 for IPv6, no private or reserved space, no source covering more than a quarter of IPv4). A source that fails keeps its previous stage object `net/stage/<name>`; the merge step writes `net/v1` from the stage objects. The same builder module runs as a Node script (`worker/scripts/build-netdata.mjs`) so the owner has a fallback if Task A0 shows that scheduled CPU time is too small for the merge.

Source evaluation is Task A16 and its table is the deliverable; this plan fixes only the policy. Candidate sources named for evaluation, each with its terms to be read by a human before anything is enabled: the cloud providers' own published range files (AWS, Google Cloud, Microsoft Azure service tags, Oracle, DigitalOcean, Cloudflare, Fastly); the Tor Project's bulk exit list; community VPN range lists on GitHub (license varies per list and some have none); search-engine crawler range files (Google, Bing, Apple, DuckDuckGo) published for verification; free IP-to-ASN datasets are not needed because Cloudflare supplies the ASN. Datasets with registration, EULA or share-alike terms (the GeoLite2 and IP2Location LITE families) are excluded by policy. Safe to redistribute in the repo: only the two hand-authored ASN lists and synthetic test fixtures. Everything else: fetch at refresh time, never vendor, until A16 records a license that permits it.

## Open decisions for the maintainer

The plan builds on the stated default for each so work is not blocked. None of these is decided; each lists options and trade-offs, not a recommendation. Questions the maintainer has already answered (city, bot handling, unique visitors, transient IP and user-agent use) are in "Decided" above.

**P-1. Source-attributed clicks (Task A14).** Without it, the funnel is exact for source to page (views by source) and page to click (clicks per link, per page), but a click cannot be tied to the source of the same visit. Options: (a) leave it, and the report shows per-page clicks per 100 views plus the source mix, never "visitors from X clicked Y"; (b) build A14: `view.js` rewrites each link's `ping` to carry the same allowlisted source label, `click_events` gains two nullable columns, and the pull, `click_daily` key and Plan 2 Task 16 change (about 9 h, touches Plan 2 files); the label is already public in aggregate form, and the combination adds one more marginal-free join dimension to clicks.

**P-2. Do clicks also go into bot buckets (Task A15)?** Today the click route drops declared bots (shipped, tested) and the maintainer's decision says bots are counted separately. Options: (a) clicks keep dropping declared bots (consistent with Plan 1, and the funnel compares human clicks with human-plus-bot views, which the report labels); (b) A15: clicks use the same classifier, store `bot_class`, and the pull and `click_daily` carry it (about 8 h, changes shipped tests `bot user agent records nothing` and Plan 2 Task 16).

**P-3. Raw view retention.** Default 7 days after rollup. Options: 1 day (least exposure of the combined raw row, no time to re-roll after a bug); 7 (default); 90 (the existing schedule, largest exposure window). Aggregates stay 90 days in the Worker and indefinitely in the local store either way.

**P-4. Global Privacy Control and Do Not Track for clicks.** Views honor both, in the browser and again at the Worker. Clicks (`ping`, no script) do not today. Options: leave clicks as they are (a GPC visitor's click is counted with no profile, so click-per-view ratios run slightly high); make the click route also ignore requests with `Sec-GPC: 1` or `DNT: 1` (about 1 h, one new test).

**P-5. Hash width and day boundary for unique visitors.** Default 32 bits, key rotated at UTC midnight. Expected colliding pairs at n visitors a day is about n squared over 2 to the power (bits + 1): at 10,000 visitors, 16 bits gives about 760 (7.6 percent undercount), 24 bits about 3 (0.03 percent), 32 bits about 0.01, 48 bits none. Fewer bits means each stored hash matches more possible IPv4 addresses (about 65,536 at 16 bits, 256 at 24, 1 at 32), which weakens, but does not remove, a membership test by someone holding both the database and the secret. Day boundary: UTC (as briefed; a returning visitor whose visits straddle UTC midnight inside one local day counts twice) or the site's local midnight (aligns uniques with local-day views and clicks; deviates from the brief). Choose the bits (16 to 64) and the boundary.

**P-6. Write quota and budget mechanism.** Defaults 120 human views per hour and 30 bot views per hour. Worst case writes: per accepted human view one budget counter write, two for the row and its `ts` index, two when the row is purged, one and one for the day hash; that is 7 per view, so 120 x 24 x 7 = 20,160 a day, plus a worst-case rollup of about 3,600 rows inserted and later deleted (7,200), about 27,400. Added to Plan 3's 67,600 that is about 95,000 of the 100,000 figure the plan uses for the free D1 plan, and Plan 3's check does not include clicks at all. Options: keep the D1 counter budget (exact, reuses Plan 3 Task 17, costs one write per view); a Rate Limiting binding with a constant key (no writes, approximate, per location; Plan 3 D-04); a paid plan (Plan 3 D-06); Workers Analytics Engine for views instead of D1 (no D1 writes, a different read API and token, retention per Cloudflare, not evaluated here). A viral spike above the hourly budget silently undercounts.

**P-7. Order against Plan 3.** Task A4 reuses Plan 3 Task 16 (`readBounded`, `flagOn`), Task 17 (`reserveRoute`) and Task 18 (`logEvent`). Those tasks currently depend on the kit routes. Options: land after Plan 3 Tasks 16 to 18 as written (the Worker half of this plan then arrives with v0.3.0 work); or first split the generic helpers of those three tasks into a small "Plan 3 group 0" that lands earlier (about 3 h of re-slicing), so page views start collecting on the test subdomain sooner and history accrues before the collector exists.

**P-8. Pull transport (Plan 2 O-1).** Task A7 uses whatever O-1 selects. A: two more fixed statements for the D1 read token. B: a second signed route `GET /e/o/views` sharing the 16F key, nonce table and limiter (this plan then adds about 8 h and the same spec amendment applies). C or D: the same module with a different transport. If O-1 is still open when A7 starts, A7 builds the interface and the D1 and file transports only.

**P-9. Dataset sources and licenses (Task A16 output).** Which feeds are enabled, in particular community VPN lists whose licenses are unclear; whether to enable the crawler-range verification at all (without it, search-engine UAs are `a/ua_bot`, never `v`).

**P-10. Refresh runner.** Worker cron (no new credential; needs enough scheduled CPU, measured in A0) or the Node script on the collector host or CI (needs a KV-write credential, which adds to threat model T-19). The plan builds one module for both and the choice is only wiring.

**P-11. Cloudflare dashboard protections the owner turns on (Task A20 documents them).** Bot Fight Mode, the AI-crawler blocking toggle and a WAF rate-limit rule for `/e/*`. Trade-off: edge blocking removes traffic before the Worker sees it, which lowers bot counts and adds a small false-positive risk for real visitors; on the free plan Bot Fight Mode cannot be bypassed per route and has no log-only mode (unverified). The owner chooses.

**P-12. AI-crawler policy in `robots.txt`.** The generated file can allow or disallow named AI training and AI search crawlers; default built is `disallow` for the listed AI crawlers and `allow` for search engines. This is advisory only.

**P-13. Privacy classification and wording review.** A daily keyed hash of an address, a city, and a derived device profile may be personal data under some privacy laws even though nothing is stored that names a person. This plan is not legal advice. The maintainer decides whether the wording in Task A11 is enough and whether to get a human review before cutover.

**P-14. `features.page_views` default.** The model default is off, so existing configs do not start collecting; the example config turns it on. Options: keep off (opt-in); default on (matches `click_tracking`).

## Review Focus

Most likely failure first. Each has a test in the owning task.

1. **Raw address, raw `User-Agent`, exact version, ASN, organization, coordinates, postal code or a full referrer reaching a table, a log line, an error message or a key.** Tests dump every table and every console call after hostile requests, including forced failures of D1, KV and the classifier. (A4, A12)
2. **Derived data recombining into a profile.** A rollup table that carries more than one of browser, OS, language, window size, city; a raw row retained past rollup; a join key between `visitor_seen` and `view_events`. (A3, A5, A12)
3. **The daily hash reversible or linkable.** Wrong key derivation, key in `[vars]`, rows surviving past the day, the same hash on two days, IPv6 privacy addresses counted separately. (A4, A5)
4. **A hot-path regression.** A KV or D1 call added to the click route; the dataset load blocking a request; CPU growth from the lookup; a dataset error turning into a 5xx. (A18, A4)
5. **Dataset poisoning and supply chain.** A source that adds `0.0.0.0/0`, private space or huge ranges, an oversized or slow response, a redirect to another host, a license problem. (A16, A18)
6. **Cardinality and write-amplification attacks.** Random referrer hosts, `utm_source`, languages, browser majors and cities pushing rollups over their caps or the pull window over its limit; a bot flood starving the human budget. (A5, A7, A4)
7. **Honoring GPC/DNT and no storage APIs.** In the script and again at the Worker. (A6, A4)
8. **Classifier overreach.** Treating VPN users or JS-off users as bots; calling an unverifiable crawler verified; paid-only fields read when the flag is off. (A19)
9. **Wrong day.** Daylight-saving rollups, uniques across UTC midnight, a closed day rewritten, double pull. (A5, A7)
10. **Funnel misread.** Clicks per 100 views above 100, source claims the data cannot support, "legitimate" numbers that hide that non-JS bots are invisible. (A8)
11. **Copy and QR events carrying an address.** (A10)
